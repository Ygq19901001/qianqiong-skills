## 🧬 技能自进化设计

本技能的进化体系分为五层。每一层只依赖下一层提供的信息，不跨层跳。

---

### 第一层：架构自知（Architecture Self-Awareness）

> 要重构逻辑，首先得说清楚"现在的逻辑是什么"。

**组件清单与核心假设：**

```
组件清单
│
├── 场景路由（S1-S8）
│   ├── 依赖：触发词表
│   ├── 核心假设：8个场景覆盖了主流学习需求的完整光谱
│   └── 易变点：新学习场景出现时需要扩展（如AI辅助学习场景）
│
├── 七阶教学法
│   ├── 七个方法：苏格拉底追问/费曼简化/类比搭建/分层递进/即时检验/脚手架递进/认知负荷管理
│   ├── 核心假设：教学效果可拆分为这七个可独立优化的方法
│   ├── 方法间关系：追问定位起点→简化给骨架→类比建连接→递进给深度→检验关环→脚手架控增量→负荷管理控总量
│   └── 易变点：方法顺序优化、新方法加入、方法间依赖关系调整
│
├── 水平推断与知识适配
│   ├── 四层水平：零基础/初学者/中级/高级
│   ├── 核心假设：用户水平可从提问的语言特征中被可靠推断
│   ├── 五维信号：用词/术语/问题结构/上下文/追问特征
│   └── 易变点：信号权重调整、新水平层级细分、交叉水平场景
│
├── 学习风格适配
│   ├── 四种风格：理论型/实践型/视觉型/听觉型
│   ├── 核心假设：适配学习风格可显著提升信息吸收效率
│   └── 易变点：风格判断准确率、混合风格策略优化
│
├── 学习路径设计
│   ├── 五阶段模型：直觉→工具→机制→实践→边界
│   ├── 核心假设：从零到一的学习遵循这五个阶段
│   └── 易变点：领域差异导致阶段模型需要定制化
│
├── 学习强化系统
│   ├── 三个机制：间隔重复/知识卡片/自测问题
│   ├── 核心假设：系统性强化能将知识从短期记忆转化为长期记忆
│   └── 易变点：复习间隔优化、卡片模板进化
│
├── 常见误区预警
│   ├── 八个场景各自典型误区 + 五个通用误区
│   ├── 核心假设：提前预警误区比事后纠偏更有效
│   └── 易变点：新误区出现、纠偏策略有效性验证
│
├── 四维质量评分
│   ├── 五个维度：清晰/准确/适配/实用/引导
│   ├── 核心假设：教学质量可被这五个维度充分衡量
│   └── 易变点：评分维度的完备性和权重
│
├── 联网搜索规则
│   ├── 来源分级：S/A/B/C四级
│   ├── 核心假设：来源可信度可被此分级可靠区分
│   └── 易变点：新来源类型出现、分级标准需要细化
│
└── 输出格式
    ├── 四种输出模式：快速答疑/深度教学/学习路径/对比辨析
    └── 核心假设：这四种格式覆盖了所有教学输出的需求
```

### 第二层：进化决策（Evolution Decision Framework）

> 不是每次教不好都要做手术。先分级，再行动。

#### 2.1 问题分级

```
┌─────────────────────────────────────────────────────┐
│ L0 噪音                                              │
│ 偶发的单次教学效果不佳。不构成模式。                      │
│ → 记录日志，不做任何改动。                            │
├─────────────────────────────────────────────────────┤
│ L1 知识缺口                                          │
│ 某个知识点反复被问到且回答质量不足。                     │
│ → 补充知识条目或优化类比库，不动框架。                   │
├─────────────────────────────────────────────────────┤
│ L2 框架微调                                          │
│ 某个教学方法需要补充规则、调整顺序、细化判断标准。         │
│ 核心逻辑不变。                                       │
│ → 走轻量验证（14天/30次教学，单轨对照即可）。            │
├─────────────────────────────────────────────────────┤
│ L3 框架重构                                          │
│ 教学流程、方法体系、水平模型需要改。核心假设变了。         │
│ → 走完整双轨验证（最少50次教学，最少14天）。              │
├─────────────────────────────────────────────────────┤
│ L4 范式替换                                          │
│ 整套教学方法论被更优方案替代。                           │
│ → 走完整双轨 + 外评估（用户反馈/学习效果追踪）。          │
│ → 旧范式存档到"历史范式库"，永久保留。                 │
└─────────────────────────────────────────────────────┘
```

#### 2.2 进化前判决清单

在启动任何 L2 及以上改动之前，必须先过这五道闸门：

```
① 穷尽了吗？
   在现有框架内调整参数（类比选择、递进速度、检验问题设计）能解决吗？
   如果能 → 不启动重构。

② 是框架问题还是执行问题？
   教学效果不好是因为方法论不对，还是这次没用好方法论？
   如果是后者 → 优化执行，不改框架。

③ 改了之后影响面多大？
   这个组件被哪些其他组件依赖？（查架构清单，第一层）
   改动会连锁影响什么？

④ 有更简单的解决方案吗？
   如果没有独立证据说明新逻辑更好 → 不要动。
   "感觉不够好"不是重构的理由。

⑤ 现在是最佳时机吗？
   技能是否处于稳定使用期？
   如果正在被高频使用 → 推迟，或先在沙箱中验证。
```

#### 2.3 不该进化的场景

- ❌ 用户满意度高且没有新的失效信号 → **稳定 > 完美**
- ❌ 仅为了"更优雅"而重构 → **拒绝**
- ❌ 没有明确的对比验证方案 → **拒绝**
- ❌ 上一次重构还在验证期内 → **排队，不叠加重构**

### 第三层：进化执行（Evolution Execution）

> L1 知识补充走标准的补充流程。L2-L4 走下面的完整流程。

#### 3.1 进化沙箱

L3 及以上改动，先在沙箱中验证：

```
沙箱条件：
- 准备50-100条历史教学记录作为测试集
- 新旧框架各自跑一遍
- 对比维度：理解准确率（检验通过率）、讲解效率（字数/效果比）、
   用户追问次数（追问少说明讲得清）、适配准确率
- 沙箱通过 → 进入双轨在线验证
- 沙箱不通过 → 修改候选框架，不进入在线阶段
```

#### 3.2 双轨在线验证

```
双轨验证协议
│
├─ ① 设定验证期
│     最少50次教学，或最少14天，取长者。
│     覆盖不同场景和水平——不能全是一种。
│
├─ ② 每次教学双轨输出
│     同一条用户问题，旧框架和新框架各自输出一遍。
│     记录：哪条轨道的输出更清晰？检验通过率更高？
│     记录：两条轨道结论不同的情况（最关键的对比数据）。
│
├─ ③ 对比维度
│     ├─ 检验通过率：用户对检验问题的回答质量
│     ├─ 追问率：回答了基本问题后还需追问的比率
│     ├─ 讲解效率：单位信息的字数/时间
│     ├─ 水平适配准确率：用户反馈"太深/太浅"的比率
│     └─ 用户满意度：用户的直接反馈
│
├─ ④ 分歧裁决
│     两轨结论不同时，回到教学第一原则：
│     "如果是面对一个真实的学生，哪种讲法效果更好？"
│     裁决结果同时记录。
│
└─ ⑤ 渐变切换（仅L3/L4）
      验证期结束后，如果新框架胜出：
      - 第1-7天：新框架处理 30% 的教学（随机抽样）
      - 第8-14天：新框架处理 60%
      - 第15天起：新框架处理 100%
      - 任何一个阶段出现显著恶化 → 暂停、分析、决定
```

#### 3.3 回滚协议

```
触发回滚的条件（满足任一）：
- 双轨验证中新框架的检验通过率 < 旧框架的 0.9 倍
- 用户明确反馈"讲不清楚" ≥3 次（在验证期内）
- 新框架的"太深/太浅"反馈率 > 旧框架的 1.5 倍
- 新框架的平均追问次数 > 旧框架的 1.5 倍

回滚操作：
- 恢复旧框架为主逻辑
- 新框架存档到"历史演化记录"，标注"验证未通过"
- 记录回滚原因和对比数据
- 版本号不递增（这次重构视为未发生）
```

#### 3.4 废弃/融合

```
验证结论 → 新框架更优
    │
    ├─ ① 保留旧框架作为"vX 历史版本"记录在技能末尾
    ├─ ② 新框架替换为主逻辑
    ├─ ③ 保留旧版本至少一个大版本周期
    └─ ④ 记录重构日志

验证结论 → 各有优劣
    │
    └─ 融合方案：取各自长，拼成新版本

验证结论 → 新框架更差
    │
    └─ 放弃方案：记录"什么情况下旧框架比新框架好"
```

### 第四层：进化治理（Evolution Governance）

#### 4.1 版本体系

```
v[major].[minor].[patch]

patch: L1 知识补充、类比优化、措辞调整
minor: L2 框架微调（调整方法顺序、细化水平信号、扩展场景）
major: L3/L4 框架重构、范式替换

版本记录格式：
---
version: 2.1.5
date: 2026-07-15
type: L2 框架微调
change: 水平推断增加"学习背景"信号维度
reason: 过去30天教学日志显示，约12%的水平误判源于未考虑用户的
        学科背景（同主题不同学科难度不同）
sandbox: 50条测试，水平判断准确率从82%提升到91%
dual_track: 14天/58次教学，新框架的水平适配满意度提升15%
user_feedback: 2次正面反馈，0次负面
---

version: 2.1.5
date: 2026-06-20
type: D13/D15 组件补齐（skill-maker-pro v2.4.0 标准升级）
change: 新增 triggers 字段、矛盾声明(D13)、ADR(D15)
reason: 响应元技能 v2.4.0 标准升级，补齐缺失的元组件
self_check: 17/17 全通
---
```

#### 4.2 进化日志（Evolution Log）

```
每次进化尝试必须记录：
- 触发原因：什么信号、什么场景触发了进化
- 尝试的方案：怎么改的
- 验证方法：沙箱+双轨，还是仅双轨
- 结果：通过/失败/部分通过
- 关键教训：这次进化教会了我们什么
- 对进化协议的影响：协议本身需要调整吗？
```

#### 4.3 跨技能进化遗传

```
当 learn-pro 完成一次 L3 重构后：
→ 提炼"重构模式"（例如：信号权重调整模式、方法顺序重排模式）
→ 存入元技能的"进化模式库"
→ 后续技能在遇到类似问题时，直接参考这个模式
```

### 第五层：元进化（Meta-Evolution）

> 进化协议本身也是可以进化的。

#### 5.1 元进化触发条件

```
- 进化协议拒绝了一次重构，但后续证明那次重构是必要的
  → 协议的"不该进化"标准需要校准

- 连续两次重构都没通过验证
  → 协议的决策逻辑可能有问题（太容易触发重构了）

- 双轨验证通过但上线后用户反馈变差
  → 协议的验证标准不够严格

- 同一个类型的框架问题在不同技能中反复出现
  → 协议缺少某种预防机制

- 技能长期没有进化，不是因为没问题，而是信号未被感知
  → 信号敏感度需要调整
```

#### 5.2 元进化的执行方式

```
① 发现元进化信号 → 记录但不立即行动
② 积累到 ≥3 个同类信号 → 提出元进化方案
③ 在下一次框架进化中，附带给元进化方案开一个"观察窗口"
④ 经过至少两次框架进化周期的对比观察 → 决定是否正式修改元协议
⑤ 元协议修改 → 更新技能模板（影响到后面所有技能的制作）
```

#### 5.3 🔒 不可变核心

有些东西不能被进化掉，否则整个体系崩溃：

```
🔒 不可变核心：

1. 双轨验证原则
   → 新旧并行验证永远不能省

2. 以结果为准原则
   → 不因为"新更优雅"而替换，必须数据说话

3. 可回滚原则
   → 任何改动必须保留回滚能力

4. 历史保留原则
   → 废弃的逻辑不删除，存档备查

5. 人类可干预原则
   → 重大进化必须可以被人类否决

这些不是"规则"，是进化协议能安全运行的底层合约。
```

### 五层关系总览

```
元进化（第五层）
  │ 审视和校准
  ▼
进化治理（第四层）
  │ 约束和记录
  ▼
进化执行（第三层）
  │ 执行
  ▼
进化决策（第二层）
  │ 触发
  ▼
架构自知（第一层）
  │ 诊断自己
  ▼
技能的核心逻辑（场景路由→教学法→风格适配→水平适配→学习路径→学习强化→质量评分→误区预警）
```
